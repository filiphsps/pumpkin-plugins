# Pumpkin plugin API

The API is a WIT world. A plugin is built against the WIT of the pinned `@pumpkinmc/pumpkin-api-ts`, and runs
on the Pumpkin release the integration tests download. Don't code against Pumpkin's `master`, the upstream
docs or memory: the API changes between releases, and a call that doesn't exist in the pinned version fails at
build time or, worse, at load time.

## Find the definition

1. **Versions.** The `@pumpkinmc/pumpkin-api-ts` entry in the `catalog:` of `pnpm-workspace.yaml`, and
   `PUMPKIN_RELEASE` in `tools/test-harness/src/pumpkin-version.ts`. They must match.
2. **The WIT**, which is the source of truth: `node_modules/@pumpkinmc/pumpkin-api-ts/wit/v0.1/*.wit` inside any
   plugin's folder (for example `packages/upnpumpkin/`). `event.wit` lists the events and their payloads,
   `command.wit` and `permission.wit` the command and permission API, and so on.
3. **The types your code compiles against**: `build/types/bindings/` in the plugin's folder, generated by
   `pnpm typecheck`. Trust these over the package's own `.d.ts`. The build rewrites 64-bit values from `bigint`
   to `number`, and passing a `BigInt` to the host panics the guest.
4. **The SDK classes** (`Plugin`, the event and command helpers) are in the package's `src/`. Read a helper
   before you use it: some of them pass `BigInt` and panic (see
   [Runtime caveats](../../../docs/building.md#runtime-caveats)).

## Check what the server does

The WIT says what you can call, not when an event fires, what cancelling it does, or which permission names
exist. For that, read the Pumpkin source at the pinned release tag (the value of `PUMPKIN_RELEASE`, which is
also the tag name):

| Question | Where, in Pumpkin |
| --- | --- |
| The WIT as the server sees it | `crates/pumpkin-plugin-wit/v0.1/` |
| What a host call does | `crates/pumpkin/src/plugin/loader/wasm/` |
| Where and when an event fires, and what cancelling it skips | `crates/pumpkin/src/plugin/api/events/`, then search for where the event is fired |
| Permission names and defaults | `crates/pumpkin/src/plugin/permissions.rs` |

Read files at the tag without cloning:

```sh
gh api "repos/Pumpkin-MC/Pumpkin/contents/crates/pumpkin/src/plugin/api/events?ref=$RELEASE" --jq '.[].name'
curl -sL "https://raw.githubusercontent.com/Pumpkin-MC/Pumpkin/$RELEASE/crates/pumpkin-plugin-wit/v0.1/event.wit"
```

`$RELEASE` is URL-encoded in the `gh api` form (`+` becomes `%2B`). In OpenCode, the `pumpkin` reference is a
checkout of `master`. Use it to find your way around and to search, then confirm the details at the tag,
because `master` is often ahead of the pinned release.

## Use the repo's wrappers first

Before calling the raw API, check whether a package in `tools/` already wraps it. They exist because the raw
calls have traps (`BigInt`, task ids, callback ids), and they come with fakes for unit tests:

| Need | Use |
| --- | --- |
| Commands and their permissions, documented in the README from the same declaration | `defineCommands` and `registerCommands` from `@pumpkin-plugins/plugin-kit` |
| Logging, repeating tasks, command callbacks | `@pumpkin-plugins/plugin-kit/host` |
| The plugin's data folder | `@pumpkin-plugins/plugin-kit/data-dir` (behind the `DataFiles` interface in `/files`) |
| Messages to other plugins | `@pumpkin-plugins/plugin-kit/ipc` |
| Errors from WASI calls | `@pumpkin-plugins/plugin-kit/wasi-error` |
| Settings | `@pumpkin-plugins/config` ([Plugin config](../../../docs/plugin-config.md)) |
| Opening a router port | `@pumpkin-plugins/upnpumpkin-api` ([Port forwarding](../../../docs/port-forwarding.md)) |
| Fakes of all of the above for unit tests | `@pumpkin-plugins/plugin-kit/testing` |

The exports are listed in each package's `package.json`. If a second plugin needs something you are about to
write against the raw API, put it in one of these packages instead.

## Files and network

A plugin can only use the filesystem or sockets when its `pumpkinPlugin.wasi` in `package.json` asks for them
(`"filesystem"`, `"sockets"`). See [Files and network access](../../../docs/creating-a-plugin.md#files-and-network-access).
Keep that code in a thin adapter behind an interface, as `WasiDataDir` does for `DataFiles`, so the logic can be
tested without a server.

## Permissions

A plugin that asks for permissions is prompted for them on the server console the first time it loads, and a
hot reload denies them, so test with a restart. Command permissions are declared with the command, and their
names are typed against the ones Pumpkin knows ([Plugin info and READMEs](../../../docs/plugin-info-and-readmes.md)).

## When the API doesn't have what you need

Stop and tell the user what is missing, and quote the WIT that comes closest. Don't work around a missing API
with undocumented host behavior, and don't bump the pinned version on your own: the API package, the server
release and the integration tests move together.
