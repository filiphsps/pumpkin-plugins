# Pumpkin++ native extension

Pumpkin++ is PumpkinMC's native extension layer for server capabilities that are not part of
Pumpkin yet or belong outside its core. Plugins can currently request chunk preparation
asynchronously: they submit work to Pumpkin's normal loading and generation pipeline, return to
their event loop, and poll later. A ready chunk remains resident under a short lease. Because the
request returns immediately, custom guest generation can run while preparation is pending.

This component is a feasibility implementation for Pumpkin `0.2.0+26.3-26.51`, source commit
`204a94ed895f041a845630d5a23c094705a0704e`. Native plugins exchange Rust trait objects and owned
values with the host. The native API integer does not establish ABI compatibility. Keep the exact
source, dependency lock, compiler, target, and tested host binary together; do not install an
artifact built for another host or platform.

## Build and run the real-server checks

Install Rust `1.98.1` and the repository's pnpm dependencies. Run these commands from the repository
root. The larger compiler stack avoids a Rust crash while compiling upstream generated block data.
The build script resolves and verifies the compiler explicitly, because a system `rustc` earlier on
`PATH` can override the compiler used by `rustup run ... cargo`. The lockfile retains the pinned upstream dependency versions; regenerating it from scratch can
select incompatible transitive prereleases.

```sh
pnpm install --frozen-lockfile
pnpm turbo run build --filter=@pumpkin-plugins/build --output-logs=errors-only
node native/pumpkin-plus-plus/build.mjs
PUMPKIN_TEST_LOG_DIR=/tmp/pumpkin-plus-plus-logs pnpm --filter @pumpkin-plugins/test-harness exec vitest run --root ../.. --config native/pumpkin-plus-plus/vitest.config.ts
PUMPKIN_PLUS_PLUS_ENGINE=static-hermes PUMPKIN_TEST_LOG_DIR=/tmp/pumpkin-plus-plus-hermes-logs pnpm --filter @pumpkin-plugins/test-harness exec vitest run --root ../.. --config native/pumpkin-plus-plus/vitest.config.ts
```

The harness downloads and checksum-verifies the pinned server. `PUMPKIN_BIN` selects an exact local
host build instead. The tests copy the native library through the harness's existing `plugins`
option; it already accepts native libraries. `PUMPKIN_PLUS_PLUS_ARTIFACT` can select a different
artifact path. Never install the `lifecycle_observer` example outside these tests: it exposes host
state solely to retain ticket-cleanup evidence.

## Installation and configuration

[Download pumpkin-plus-plus 0.1.0](https://github.com/filiphsps/pumpkin-plugins/releases/tag/pumpkin-plus-plus-v0.1.0)
<!-- docs:end native-release -->

Copy only the tested native library into your server's `plugins` directory and restart. Its
metadata name is exactly `Pumpkin++`; the library filename can differ. Any loaded plugin that can
send host IPC to Pumpkin++ can call its protocol. The host-supplied sender name scopes operation
IDs, leases and quotas, and identifies the caller's work for cleanup when that plugin unloads.

On first load, Pumpkin++ creates `plugins/data/Pumpkin++/config.json` as `{}`. You can override its
finite job timings there:

```json
{
    "deadlineMs": 30000,
    "leaseMs": 30000,
    "terminalRetentionMs": 30000
}
```

These fields are optional. Deadlines and terminal retention must be between 1 and 30000
milliseconds; leases must be between 1 and 60000 milliseconds. A lease starts when the job becomes
ready and cannot be renewed. The configuration file is limited to 8192 bytes. Invalid configuration
fails plugin loading.

The host IPC sender supplies the caller identity; request fields cannot select it. IDs and leases
belong to the submitting sender. The pinned host does not expose a caller instance identifier, so a
same-name reload shares the same per-caller quotas. Finite expiry and unload cleanup still apply.

## Protocol v1

Requests and responses are UTF-8 JSON, each at most 8192 bytes, with top-level `v: 1`. Worlds are
1–128 UTF-8 bytes; operation and lease IDs are 1–64 bytes. Unknown fields,
malformed UTF-8, malformed JSON and invalid field types produce `invalid_request`. An unsupported
integer protocol version produces `incompatible`.

```json
{"v":1,"op":"probe"}
{"v":1,"op":"submit","world":"world","x":-200,"z":201}
{"v":1,"op":"poll","operationId":"<submit response>"}
{"v":1,"op":"cancel","operationId":"<submit response>"}
{"v":1,"op":"release","leaseId":"<ready response>"}
```

World names follow the host's world folder or dimension names. Coordinates are signed chunk
coordinates, restricted to **-1000000 through 1000000 inclusive** on each axis. This conservative
bound keeps block-coordinate conversion, generation neighbors and ticket propagation away from
i32 overflow. Full i32 wire types do not imply that edge coordinates are safe for the host.

Submit returns `operationId` and `state: "queued"`. Poll returns `queued`, `running`, or `ready`;
ready always includes `leaseId` and `remainingLeaseMs` from 1 through 60000. Every response includes
`v: 1` and `ok`. A terminal poll returns `ok: false`, the operation ID, and `code` equal to `timeout`,
`host_failure`, `cancelled`, or `expired`. Other errors contain `code` without an operation ID:
`incompatible`, `busy`, `invalid_request`, `unknown_world`, `host_failure`, or `not_found`.

Cancel succeeds with the operation ID and `state: "cancelled"`; release succeeds with the lease ID
and `released: true`. Repeating release for the same lease succeeds while its `Released` record
remains in terminal history. The record expires after `terminalRetentionMs` and may be evicted sooner
when terminal-history limits are reached; after removal, release returns `not_found`. Released
operations subsequently poll as expired.

## Limits and cleanup

The bridge admits at most 64 live jobs globally and 16 per caller, including at most 32 queued
jobs globally and 8 per caller. Running jobs and ready leases share an active limit of 32 globally
and 16 per caller. At most 16 physical chunks are prepared or leased at once, enough to hold every
chunk in one 64-by-64-block LOD section through sampling. Jobs for the same
world instance and coordinates share one host ticket, while each caller retains its own operation
and lease. Terminal history is capped at 64 globally and 16 per caller and expires after its
configured retention period; evicted IDs return `not_found`.

There are at most 8 persistent world observers, all attached to the currently loaded world set.
The pinned host's global listener channel is unbounded. The worker continuously drains it without
retaining unrelated publications, and detaches an observer when its backlog exceeds 4096 entries
or the channel closes. Affected jobs fail and release their tickets. That world cannot attach
another observer until it unloads. This bounds bridge-owned observer state and prevents repeated
abandoned subscriptions; it cannot impose a hard allocation limit on the upstream unbounded
channel between worker runs. The host removes a detached sender on its next publication.

A ready response requires a live current world, a live lease, and the same published chunk Arc in
the ordinary loaded-chunk map. Air content is never a failure signal. The bridge never calls
`Level::get_or_fetch_chunk`: cancelling that pending future can leak its private ticket, and its
closed-listener path can insert an empty fallback. Bridge-owned tickets instead have one removal
path shared by cancellation, deadline, lease expiry, caller disappearance, world unload and bridge
unload. A dedicated bridge thread polls those resources every 10 milliseconds using Pumpkin's
synchronized world and chunk-loading state; generation itself remains in the host chunk system. On
unload, the bridge stops and joins the thread, which drains jobs, tickets and observers before
returning control to the native loader.
